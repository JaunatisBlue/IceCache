# 联合诊断结果（2026-09-12）：计时拆分 + 地址可合并性

> 目的：一次运行回答"系统方向（子树感知 gather / head-major 布局 / 动态减少 k）值不值得继续"
> 结论：**诊断本身成功了，但发现一个硬件级前提被破坏——可用 GPU 跑在 PCIe 3.0 ×1 上**，导致"传输主导"的所有结论都被放大 ~15×。**方向判定必须等链路修复后才能下。**
> 产物：`experiment/run_17_diag.sh`、`apply_diag_patch.py`、`analyze_diag.py`、`h2d_calibrate.py`、`link_confirm.py`；dump `experiment/logs/dci_opt/diag_smoke_qasper2.npz`。

## 0. 一句话结论

| 项 | 结果 |
|---|---|
| 补丁是否改变结果 | **否**。F1 45.52 vs 锚点 45.48（Δ+0.04，噪声内） |
| 计时拆分 | CPU 地址准备 + `copy_to_buffer` ≈ 21.9 ms/token（= `recall_gather` 21.2 ✓）；H2D ≈ 50.2 ms/token（≈ `recall_wait` 47.9 ✓） |
| 地址结构 | 同 head 相邻 leaf 实测间隔 **131072 B**，即 `2×page_size(16)×n_kv_heads(8)×head_dim(128)×4B` = `cpu_n_bytes_per_page` → **规则 stride，非连续**（证实 codex 的批评） |
| 可合并性 | 同 head 内 merge_ratio **0.213**；跨 head 重复选叶 **0.367** |
| ⚠️ 硬件 | 可用 GPU `0000:3b:00.0` 链路 **width=1 / max=16** → 实测 H2D=D2H=**0.82 GB/s**（= PCIe 3.0 ×1） |
| 判定 | **不能判定。** 需先修链路，否则"传输主导"是环境伪影 |

## 1. 做了什么

1. 给 `infer_state.py` 打**纯附加、env 门控**（`ICECACHE_DIAG`）的诊断补丁：CUDA events 括住 H2D 与 cast；把 `recall_gather` 细分为「地址准备」与「`copy_to_buffer`」；dump 每 `(layer, head)` 的 leaf id 与真实源地址。
2. 无回归运行（`ICECACHE_DIAG=0`，qasper20）→ F1 **45.52**（锚点 45.48）。
3. 取证运行（`ICECACHE_DIAG=1`，qasper2，2000 记录 / 1000 events）。
4. 离线分析（`analyze_diag.py`）：run 结构、stride、跨 head 冲突。
5. H2D 微基准（`h2d_calibrate.py`）→ 发现带宽异常。
6. 链路核查（`nvidia-smi` + sysfs）→ 定位到 PCIe ×1。

## 2. 计时拆分（DIAG 运行，2 samples）

| 段 | 每次 recall | 折算 /token（30 次） | 与既有 profile 对照 |
|---|---:|---:|---|
| CPU 地址准备 | 0.487 ms | 14.6 ms | — |
| `copy_to_buffer`（CPU gather） | 0.243 ms | 7.3 ms | 两者合计 ≈ `recall_gather` 21.2 ✓ |
| **H2D**（CUDA event） | **1.672 ms** | **50.2 ms** | ≈ `recall_wait` 47.9 ✓ |
| cast（CUDA event） | 0.0028 ms | 0.08 ms | 可忽略 |

**关键结构性事实**：`recall_wait` ≈ H2D 时长 → **H2D 没有被隐藏，而是被直接等待**。之前"召回占 TPOT 46%"里的 `wait` 大块，本质就是 H2D。

---

## 3. 地址结构（核实了 codex 的批评）

- 2000 条记录、33062 个 (head,leaf) 选中页、240 个 (layer,head) 分组、250 个含 ≥2 head 的召回步。
- **实测 stride = 131072 B**（1788/1791 次），正好等于 `cpu_n_bytes_per_page = 2×16×8×128×4`。
  → 同 head 内 leaf `j` 与 `j+1` 相隔一个**完整多头页**：**规则 stride，不可直接合一次 memcpy**。v1/v2 的"叶子连续"彻底否定。
- **同 head 内 merge_ratio = 0.213**（选中页里 21.3% 落在连续 leaf 段，可改为 strided 拷贝）。
- **跨 head merge_ratio = 0.367**（36.7% 的选中页被同一步的多个 head 共享；同一 leaf block 内各 head 的页连续，可合并）。

---

## 4. ⚠️ 硬件前提被破坏：PCIe 3.0 ×1

| 证据 | 值 |
|---|---|
| `nvidia-smi` 可用设备 | 仅 `index 0`, `00000000:3B:00.0` |
| `pcie.link.width.current / max` | **1 / 16**（稳定，非省电降频） |
| `pcie.link.gen.current / max` | 3 / 3（PCIe 3.0，8 GT/s） |
| sysfs | `width=1 speed=8.0GT/s maxwidth=16 maxspeed=16.0GT/s` |
| 实测 H2D / D2H | **0.82 / 0.82 GB/s**（对称 → 链路限制） |
| 实测 D2D | **786.5 GB/s**（GPU 本身健康） |
| 规模相关性 | 64 KB → 8 MB **全部 0.82 GB/s**（无每次调用开销，纯带宽限制） |
| 另一张卡 | `0000:af:00.0` **width=16（健康）**，但 `nvidia-smi -i 1` → "No devices were found"（不可用） |

**含义**：
- PCIe 3.0 ×1 理论 ≈ 0.985 GB/s，实测 0.82 GB/s ✓ 完全吻合。
- 健康的 PCIe 3.0 ×16 ≈ **12 GB/s** → 当前只有 **~1/15**。
- ⇒ 本仓库**所有**传输相关数字（`recall_wait` 44–48 ms/token、"召回占 46%"）都被放大约 15×。

## 5. 链路归一化后的重新判定

| | 现状（×1） | 归一化到 ×16 |
|---|---:|---:|
| H2D /token | 50.2 ms | **≈ 3.3 ms** |
| CPU gather /token | 21.9 ms | 21.9 ms（不变） |
| recall 合计 | ≈ 72 ms | ≈ 25 ms |
| 主导项 | **H2D 字节量** | **CPU gather** |

**两个互斥结论**：
- 若在**当前 ×1 环境**做研究 → 只有"减少字节"（动态 k）有收益，布局合并毫无意义。
- 若在**健康 ×16 环境** → CPU gather 重新成为召回侧主导项，**子树感知合并 gather / head-major 布局**才有意义。

**所以：这次诊断不能给出方向判定，必须先修链路。** 在 ×1 上得出的任何"应转向动态减少 k"的结论都是环境伪影。

## 6. 下一步（按优先级）

| 优先 | 动作 | 说明 |
|---|---|---|
| **①** | **修 PCIe 链路**：把可用卡换到 ×16 槽位 / 修复 `af:00.0` 那张 ×16 卡 / 换机器 | 这是所有传输结论的前提。`af:00.0` 已在 ×16，`nvidia-smi` 却看不到它 → 建议先查它的 Xid/ECC 状态并尝试 GPU reset（需 root，本机 sudo 要密码） |
| **②** | 修复后**原样重跑 `run_17_diag.sh`** | 现成工具链，一条命令；对比 §2 五段分解是否翻转 |
| **③** | 无论链路如何都可先做的**零 GPU 项**：把 merge 分析从"leaf 连续"扩展到"DCI 父节点/子树跨度" | 我目前只存了 leaf id + 地址；要判子树感知合并需补 parent 映射 |
| **④** | 给论文留证据：把"PCIe ×1"作为**环境注记**写进实验设置 | 否则复现者无法理解 0.82 GB/s |
