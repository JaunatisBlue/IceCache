# 带宽受限下的 KV Offload 探索（实验 18–21，2026-09-12）

> 前提：另一张 GPU 不可修复，**只能用 `0000:3b:00.0`（PCIe 3.0 ×1，实测 0.82 GB/s）**。
> 这个约束反而给了一个别人不会有的角度：**当 CPU→GPU 传输不再免费时，KV offload 该怎么设计**。
> 全部数据：Llama-3.1-8B-Instruct、Qasper20、page 16、reuse 3、FP16 recall、promotion 0.01、同一天同一张卡。

---

## 0. 结论速览

| # | 发现 | 性质 |
|---|---|---|
| 1 | **预取（layer prefetch）在任何配置下都不减反增** | 负结果，杀死了"藏传输"路线 |
| 2 | **质量对字节是悬崖**：砍 residency（budget）64→48 掉 **4.28 F1**，48→32 只再掉 0.51 | 表征 |
| 3 | **等延迟等字节下，换旋钮差 3.5–3.7 F1**：砍工作集（`page_topks`）远优于砍常驻集（`page_budgets`） | **系统改进（配置策略）** |
| 4 | **`recall()` 的 gather 成本与页数无关**（5182 页→18.4 ms，1480 页→16.2 ms）→ 是每次调用的固定开销 | 诊断 |

## 1. 实验 18 · 预取藏不住传输（负结果）

代码里本来就有 layer prefetch（`--n_prefetch_layers`，默认 0）：把下一层的选择+搬运提前异步发起，与当前层 GPU 计算重叠。我们的 qasper 配置从未开启它。

| 配置 | TPOT | recall_wait | recall_gather | F1 |
|---|---:|---:|---:|---:|
| baseline（无预取） | 141.62 | 44.65 | 18.28 | 45.52 |
| `--n_prefetch_layers 1` | **149.11（慢 5.3%）** | 43.12 | **28.24** | 45.96 |
| topk32 + 预取 | 111.61 | 21.66 | 25.01 | 44.77 |
| topk32 无预取 | 109.70 | 22.94 | 16.84 | 44.44 |
| topk48 + 预取 | 102.00 | 6.81 | 26.32 | **39.35** |
| topk48 无预取 | 96.63 | 7.74 | 16.17 | 43.00 |

**即使把每层 recall 链路压到远小于 GPU 计算（topk48 时 wait 只剩 7.7 ms），预取仍然更慢，且白掉 3.65 F1。**
原因：预取把下一层的地址构建 + DCI 查询压到主线程同期的 CPU 上（gather 16→26，+63%），并把"用当前 hidden state 投影下一层 q_proj"的**陈旧 query** 用于选页。

> **结论：在这个系统上，"藏"不是可用选项——只能"减"。** 这直接否掉了 FreeKV/InfiniGen 那一路的 latency-hiding 在本平台的可行性。

## 2. 实验 19 · 质量对字节是悬崖

| budget | TPOT | pages/tok | wait | F1 |
|---:|---:|---:|---:|---:|
| 64 | 141.6 | 5182 | 44.7 | **45.52** |
| 48 | 127.1 | 4212 | 35.1 | **41.24** |
| 32 | 108.2 | 2971 | 22.8 | **40.73** |

- 64→48：字节 −18.7%、TPOT −10.2%，代价 **−4.28 F1**
- 48→32：字节 −29.5%、TPOT −14.9%，代价只有 **−0.51 F1**

**边际质量成本在 64→48 之间塌陷。** 均匀砍预算是一个性价比极差的旋钮——这也解释了为什么 exp12 的 topk 扫描看起来"更划算"。

（另外，`wait` 与页数严格线性：五个配置点全部落在 **7.7–8.6 µs/页**，折算 8 KB/页 @ 0.82 GB/s ✓，再次确认纯带宽受限。）

## 3. 实验 20 · 换旋钮：等延迟下 +3.5~3.7 F1 ⭐ 核心结果

关键机制澄清：**`page_topks` 是"每步保留多少页不重选"**，`num_neighbours = n_dci_pages − topk`。
所以 **topk 越大 → 实际召回越少 → 传输越少**；而 `budget` 是常驻集大小。
注意：**`page_topks` 的库默认值是 `budget // 2`（=32），而本仓库所有实验都显式设了 `--page-topks 0`，即召回量拉满——是最贵的设置。**

| 目标延迟 | 砍工作集（budget 64） | 砍常驻集（topk 0） | 差值 |
|---|---|---|---|
| **~110 ms** | topk32：2995 页 / **F1 44.44** | budget32：2971 页 / **F1 40.73** | **+3.71 F1** |
| **~127 ms** | topk16：4164 页 / **F1 44.75** | budget48：4212 页 / **F1 41.24** | **+3.51 F1** |

**同样的延迟、同样的字节量，只是换了一个旋钮，质量差 3.5–3.7 F1。**

解释：`budget` 缩小的是**常驻 KV 池**（信息被永久丢弃）；`page_topks` 只是在**每步注意力的若干槽位上用"保留页"而不是"重选页"**，常驻内容不丢。所以前者是不可逆的信息损失，后者只是选择新鲜度的折衷。

**这是一条可落地的系统策略**：带宽受限时，降 `page_topks`（提高保留、减少重取），不要降 `page_budgets`。

## 4. 实验 21 · recall 地址构建优化：TPOT −6.9%，F1 不变 ⭐ 已默认开启

**诊断**：gather 成本与传输页数几乎无关（5182 页 18.39 ms vs 1480 页 16.17 ms）→ 它不是数据搬运，而是**每次调用的固定开销**。原代码在 `recall()` 里：

```python
for i in range(self.n_kv_heads):
    self._src_address_buffer[counter:counter+nr_cpu[i].item()] = \
        self.page_address_buffer[layer_idx][b, i, rids_cpu[i, :nr_cpu[i]]]
    counter += nr_cpu[i].item()
```
每 token 执行 8 × 30 = **240 次**，每次都 `tensor.item()`（同步）并用 **torch 张量去索引 NumPy 数组**（触发反复的 tensor→array 转换）。

**改动**：先把 `rids`/`nr` 一次转成 NumPy 视图，循环内不再做任何张量操作。

| | TPOT | recall_gather | recall_wait | pages/tok | F1 |
|---|---:|---:|---:|---:|---:|
| `ICECACHE_FAST_ADDR=0` | 141.94 | **18.39** | 44.79 | 5185.7 | 45.88 |
| `ICECACHE_FAST_ADDR=1` | **132.19** | **9.87** | 45.06 | 5206.8 | 45.75 |

- **gather −46.3%（−8.5 ms/token）→ TPOT −6.9%（−9.75 ms）**
- **F1 −0.13（噪声内）**；页数不变 → 同样的活、更少的开销
- `wait` 未变 → 传输路径未被触碰（符合预期）
- **已设为默认开启**，`ICECACHE_FAST_ADDR=0` 可回退

> 这是纯实现层的系统优化，**不依赖链路质量**（CPU 侧开销在任何链路都存在），因此对健康 GPU 同样有效。

## 5. 机制澄清（避免走弯路）

1. **IceCache 已经只传增量**。`_DCI_query` 用 `DCI.diff_pages_by_head(nn_idx_0, selected_page_idx, ccc, cc2gp)` 算出 `recall_idx`（不在池里的页），`nr = (recall_idx >= 0).sum(1)` 就是增量数。→ **"减少重复传输"不是可做的创新点。**
2. **`recall()` 被调用 30 次/token**（30 层都有 offload 预算），其中只有 10 层跑真正的 DCI 查询（`dci_select` 10 次/token），其余 20 层复用选择但要各自 gather + H2D。
3. **成本模型**：`传输 ms ≈ 页数 × 8.1 µs`（8 KB/页 @ 0.82 GB/s）；TPOT 的下降可以被转移量 + native query + gather 三项完全解释（加性、几乎无重叠）。

## 6. 下一步（按价值排序）

1. **把"等延迟换旋钮"做成策略**（已可交付）：在当前 20 样本上，`topk32` 相对 `topk0` 是 **−22.5% TPOT / −1.08 F1**，而 `budget32` 是 −23.6% / −4.79 F1。建议把默认配置从 `page_topks 0` 改为 **`budget//2`**，并在更大子集上确认。
2. **继续压 CPU 侧**（与链路无关、收益确定）：
   - `nr.cpu()`/`rids.cpu()` 仍是 2 次 D2H/recall = 60 次/token；`rids` 只在 CPU 使用，可完全留在 CPU（省 30 次 D2H/token）；
   - `page_metadata` 6.67 ms/token、`index_update` 3.56、`query_postprocess` 4.35 都还没优化过。
3. **按层分配 topk**（算法向）：`--page-topks` 接受列表。需要先补"逐层敏感度"数据（exp 10 的 skip 路线已因架构崩溃否决，但"逐层 topk"不需要跳过 DCI，架构上是安全的）。
4. **若将来链路修好**：用同样的脚本重跑，验证"传输不在关键路径"时上述策略是否仍成立。
