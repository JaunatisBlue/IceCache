## 2. Phase 2 · 阶段级 A/B（4 组 36k passkey，2 次重复交错）

每跑 4 个 36k prompt（`loc` = 0/0.25/0.5/0.75），`--profile-new-tokens 96` ⇒ **四跑的 measured decode steps 全为 348**（两臂等长，无构成混杂）。

| 阶段 (ms/token) | A 基线 | B 向量化 | Δ | A 臂内 sd | B 臂内 sd |
|---|---:|---:|---:|---:|---:|
| **address prepare** | 1.3812 | **0.5665** | **−58.98%** | 0.040 | 0.047 |
| └ per-leaf `data_ptr()` 循环 | 0.9462 | **0.2082** | **−78.00%** | 0.039 | 0.017 |
| index update total | 4.5636 | 3.9382 | −13.71% | 0.062 | 0.391 |
| native DCI insert | 0.9284 | 0.9595 | +3.35% | 0.005 | 0.071 |
| CPU page alloc | 0.3572 | 0.3499 | −2.02% | 0.002 | 0.025 |
| reuse_update_node | 0.2999 | 0.3154 | +5.16% | 0.020 | 0.046 |
| recall_wait | 38.677 | 38.580 | −0.25% | 0.041 | 0.490 |
| **native_query** | 32.740 | 36.903 | **+12.72%** | 2.871 | 0.943 |
| recall_gather | 10.293 | 10.969 | +6.57% | 0.238 | 0.522 |
| page_metadata | 6.808 | 6.870 | +0.91% | 0.061 | 0.263 |
| **TPOT 聚合** | **150.78** | **154.75** | **+2.64%** | 1.845 | 7.145 |

**怎么读**：

- **地址阶段的结果极硬**：Δ −0.815 ms/token，是自身臂内 sd（0.040）的 **20 倍**；per-leaf 是 19 倍。
- **TPOT 在这一项里不可分辨**，而且是**反向**。原因不在补丁，见下。

### 2.1 为什么这一档的 TPOT 没有分辨力（以及为什么不必重测）

把四个跑按 `native_query` 与 TPOT 排开：

| run | `native_query` | TPOT | `address prepare` |
|---|---:|---:|---:|
| A1 | 34.77 | 152.08 | 1.3527 |
| A2 | **30.71** | 149.47 | 1.4096 |
| B1 | 36.24 | **149.70** | 0.5335 |
| B2 | **37.57** | **159.80** | 0.5995 |

- `corr(native_query, TPOT) = **+0.663**`（n=4，仅示意）。
- `native_query` 占 TPOT **22.8%**（34.82 / 152.76）；**A 臂两次之间就跳了 −13%**（34.77→30.71，臂内 sd 2.87 = 8.8%）。
- ⇒ **run 级噪声 ≈ 2.1 ms/token = TPOT 的 1.37%**。而 **36k 上补丁的信号只有 0.53%**（address prepare −0.8147 ms/token ÷ 152.76；`index_update` −0.63 = 0.41%）。
- ⇒ **信噪比 1 : 2.6**，2 次重复在原理上测不出来。噪声还是**跨跑**的（每个 test 各建一次树，树形不可复现），逐样本配对也消不掉。

**排除"补丁让 36k 变慢"这个可能，不需要重测**——同一批运行的阶段账目就能排除：

| 补丁**触及**的段 | Δ |
|---|---|
| address prepare | **−0.8147** |
| per-leaf `data_ptr()` 循环 | **−0.7380** |
| index update total | **−0.6254** |

| 补丁**不碰**的段 | Δ |
|---|---|
| `native_query` | **+4.1629** |
| `recall_gather` | +0.6764 |
| `reuse_update_node` | +0.0155 |
| `native DCI insert` | +0.0311 |

**下降的全部是补丁改写的代码路径，上升的全部是与补丁无关的段** ⇒ 符号不可能来自补丁。

**要重测到有分辨力需要多大代价**：run 级噪声 ∝ 1/√num_tests。按 4 test/跑 = 1.37% 外推：

| num_tests/跑 | 噪声（占 TPOT） | 单跑耗时（估） |
|---:|---:|---:|
| 4（已做） | 1.37% | ~2.7 min |
| 16 | 0.69% | ~11 min |
| 36 | 0.46% | ~24 min |
| 64 | 0.34% | ~43 min |

即便 64 test/跑（2 臂 × 2 重复 ≈ **2.9 小时**），噪声 0.34% 才刚好压住 0.53% 的信号。**性价比不成立，不建议重测。**

**替代方案（已具备）**：同一代码路径、同一补丁，在**噪声小得多的工况**上测端到端——全量 Qasper 200 条逐样本配对（n=192）：**−2.092 ms（−1.49%），95% CI [−3.095, −1.088] 排除零**；Phase 4 交错 3 次/臂：**−3.154 ms（−2.32%）**。

> **设计上的教训（我认账）**：36k 是测 TPOT 最差的工况——**分子小（分母大 ⇒ 效果占比只有 0.53%）且分母抖（树形噪声 1.37%）**。36k 只适合用来测**阶段级**与**精度**；端到端 TPOT 应放在样本量足够、树形噪声占比低的工况上并用多种子配对。

## 5. 合并判断

| 端到端读数 | n | Δ TPOT | 置信 |
|---|---:|---:|---|
| Phase 4 聚合（3+3 跑，丢弃 warm-up） | 6 跑 | **−3.154 ms（−2.32%）** | SE 1.07，排除零 |
| Phase 4 逐样本配对（3 对） | 19×3 | −3.15 / −3.71 / −6.17（均值 **−4.34，−3.0%**） | 2/3 排除零 |
| **Phase 3 全量逐样本配对** | **192** | **−2.092 ms（−1.49%）** | **CI [−3.095, −1.088]，排除零，74.5% 样本更快** |

**三个独立读数同向，量级 1.5% ~ 3.0%。** 最大样本（n=192）的那个最可信：**−1.49%**。

**与阶段级账目的差额（诚实标注）**：
- 补丁**直接**造成的：`index_update` −1.137 ms/token ⇒ 相对 136 ms 是 **−0.84%**。
- 实测端到端 −1.49%（n=192）到 −2.32%（n=6 跑）。
- 差额（≈0.7~1.5 ms/token）来自 `native_query`(−0.88) 与 `recall_gather`(−0.33) 的同步下移 —— 这两个阶段**补丁完全不碰**，且位移在各自臂内 sd 的 1-1.4 倍内（噪声）。所以**保守可归因的口径是 −0.84%，实测口径是 −1.5%~−2.3%**。
- **未做实验的候选解释**（不要再当成结论）：旧路径每 boundary 创建 ~400 个 torch 视图/临时对象，其引用计数/GC 与 ATen 派发开销有一部分落在计时窗口之外；或主线程 Python 时间减少降低了与 executor 线程的 GIL 争用。

## 7. 收尾判断

- 四道门全过：**等价性（逐元素）→ 阶段级（−58%~−84%）→ 全量质量（200 条 +0.27 F1）→ 端到端（−1.5%~−2.3%，CI 排除零）**。
- 天花板要认清：整条增量更新只占 TPOT 的 2-3%，本体收益 ≈1%；`recall_wait`(24%) 是链路、`native_query`(25%) 是下一个大项。**继续在 1% 里磨的边际收益已很低。**
- 因此 `sys-optimize` 适合定位为**"系统底座清理完成"**：等价性与成本账目都已凿实，可以放心往 agent 场景转；CPU 侧的下一步若还要做，应回到 §8 的两项（promotion 层间梯度的质量门、`page_metadata` 6.8 ms/token 的首次量化），而不是继续压地址路径。
