## 第一部分 · 已生效的工作（有实测效果，均已合并到 `algorithm`）

### 1. Design A 本体：`page_scan` 取代 DCI 的树构建 + 树检索

保留语义 page，替换 B+ 树：精确 kNN 贪心打包 + 对 page 均值的 matmul 扫描。
这是整个项目的基线，也是后面所有优化挂靠的对象。报告 `design_a_spec.md`。

| 轴 | DCI | page_scan | 结果 |
|---|---|---|---|
| 准确率（n=200 hotpotqa） | 0.5358 | **0.5578** | +0.021 |
| TPOT | 0.1280 s | **0.0994 s** | **1.29x 快**，CI 不含 0 |
| 查询延迟 | 2.03 ms/层 | 0.79 ms/层 | 2.6x |
| TTFT | — | — | 1.64x 落后（后经 2、4 项修到 1.16x） |

### 2. 贪心跨层批量化 — `eacd05c`

把 12 个 builder 层的贪心合成一次跑（96 heads 而不是 8）。**build 3408 ms → 798 ms。**
关键：必须用 `use_sim=False`（物化的 `[M,N,N]` 在 96 heads 下是 99 GB）。逐位相等 0/188320 项。

### 3. 地址布局向量化 + CPU 页写入线程化 — `05d37f6`

两个纯开销项：`_page_scan_layout` 的 849 ms 逐元素 `ctypes` 循环（地址是仿射的，一次 numpy 加法替代，**849 → 245 ms**），
`_page_scan_write` 的串行 scatter（改为 8 线程池，**flushing wall 2384 → 1272 ms**）。
**TTFT 6.912 → 5.732 s，对 DCI 1.402x → 1.163x。**

### 4. 分支 D：逐位相同的贪心加速 — `8a6fe18`（报告 `11_exact_greedy_fast.md`）

`use_sim=False` 时只扫描仍可选的 token，重建成本摊到一个 span（默认 `sqrt(2*n_built)`）。

- 离线贪心 M=96 N=16072：**809.4 → 637.8 ms（1.29x）**
- live TTFT 配对 n=20：**−0.0932 s**，17/20 更快
- 准确率：**20/20 分数与生成 token 完全相同**（逐位，`torch.equal`，主会话独立复验）

**为什么它是零风险：** gemv 按列独立累加，删列不改变存活列的位。但这是**kernel 的性质不是数学的性质，CPU 上不成立**
（CPU BLAS 按形状选分块，实测 6/2015 项差 1 ULP）——所以 live 路径只在 CUDA 上分派。

### 5. 共享 staging 裁剪 — `97a60bb`（报告 `12_staging_decode_trim.md`）★ 最大的 decode 收益

在 `estimate_select_recall` 里，两条后端**完全相同地**支付的那部分开销。

| 后端 | TPOT 基线 | 优化后 | 配对 Δ | 胜/负/平 | 符号检验 |
|---|---|---|---|---|---|
| **page_scan** (40 行) | 105.60 ms | **82.10 ms** | **−22.26%** | **40/0/0** | 1.8e-12 |
| — 同代码空跑 | 105.60 | 99.82 | −5.47% | 29/11 | 0.006 |
| **DCI** (20 行) | 119.74 ms | **105.70 ms** | **−11.72%** | 17/3/0 | 2.6e-3 |
| — DCI 空跑 | 119.74 | 120.84 | +0.92% | 14/6 | 0.115 |

净收益 **−17.7% ~ −22.3%**。**形状是证据：effect 40 行全负，空跑两个符号都有（11 行正）。**
输出同一性：page_scan **40/40 文本+分数完全相同**，而该臂自证可复现（基线 vs 基线 0/40）。

> 重测了合并后的树，并**把 staging 单独作为一条臂**跑进同一个测量窗口。它的同代码空跑比这里干净得多
> （−1.96% / +2.64% / −2.63% / +0.04%，对比本表的 −5.47% 单侧空跑），结论是：
>
> | 臂 | 调整后 TPOT Δ |
> |---|---|
> | **仅 staging** | **−13.27% ~ −14.85%**（34/6、33/7） |
> | 完整合并 | −15.06% ~ −15.38% |
> | 合并 − staging（＝查询裁剪的贡献） | −0.69 ms（−0.79%），30/10，p=2.2e-3 |
>
> **所以本表的 −22.3% 原始值不复现，诚实的量级约 −14%；三条分支合并后是 −15% ± 2。**
> 丢效应的不是合并——**是 staging 自己的头条量级在更干净的窗口里复现不出来**。
> 主导不确定度是**跨窗口散布 ~5.3 ms（~6%）**：本表 opt 臂绝对值 82.1 ms，复测的 staging 单臂在
> **完全相同的代码**上是 **87.35 ms**，比它测到的任何窗内空跑都大。

三项改动：逐头 Python gather 向量化（369 µs → 31 µs/次调用）、去掉一个设备同步、
以及结构性的那一项——**34 层里有 22 层是 alias，却每次都从零重推「anchor eids + 常数 c2p 偏移」**。

### 6. page_scan 查询常量提升 — `2ed1e22`（报告 `13_page_scan_query_constants.md`）

把四个与 `q` 无关的逐调用张量提成缓存。查询 p50 **−7.3% ~ −9.0%**（我独立重算：
base1 0.8314 → opt 0.7709 → base2 0.8469 ms，168/200，p=9e-24；同代码空跑 +0.0154 ms 符号相反）。
**预测 200/200 完全相同。**机制上限 12×0.0605 = **0.73 ms/token ≈ 0.7% TPOT**——是管道性修剪，不是成果。

### 7. prefill 卸载拷贝 — `4de2c87`（报告 `14_prefill_offload_copy.md`）

`prefill_backup_pages` 做的是 **fp16 device → fp32 pinned host 的 `copy_`**，
**CUDA 不能 DMA 跨 dtype 拷贝**，退化成逐元素写主机内存：

| 变体（16k 形状，998 页） | ms | GB/s |
|---|---|---|
| fp16 dev → fp16 pinned，裸 DMA | 4.99 | 26.2 |
| fp32 dev → fp32 pinned，裸 DMA | 9.97 | 13.1 |
| **fp16 → fp32，原来的 `copy_`** | **57.43** | **2.28** |
| device 上转型再 DMA（改后） | **10.28** | **12.7** |

配对 n=9：**DCI TTFT −1.670 s（9/0，p=0.002）**，**page_scan −1.614 s（9/0）**。16k 行是 0.65×/0.70×。
第二个独立效果：设备级 `cuda.synchronize()` 换成拷贝自己流上的同步（那个设备级同步等主线程 kernel，值 272 ms/行）。

**但必须说清楚：这条路两条臂共用，所以 page_scan/DCI 的 TTFT 比值反而变差（1.160 → 1.247）。**

### 8. 两个静默 bug 的修复（含在 Design A 里）

- **`masked_fill` 取代 `scores + _bias_t`**：后者擦不掉 NaN（`inf*0=NaN`，`NaN+(-inf)=NaN`，`topk` 把 NaN 排最前），
  会返回 `>= n_built` 的页号，即 KV 从未写入的地址。
- **CUDA scatter 未定义行为**：`out[rows[sel], rank[sel]] = flat[sel]` 里重复候选与下一个首次出现共享输出槽，
  CUDA 上是未定义的——实测发出重复页号并丢掉一个不同页号（需要 12 个唯一 id 只给出 11 个），准确率腰斩到 0.1482。
  合成随机键几乎从不碰撞，真实键经常碰撞，所以单元测试通过了。
- **`scatter_pages(None, None)` 崩溃（2026-09-26，未提交）**：`estimate_select_recall` 在
  `use_dci` 为假时按设计返回 `(None, None)`（`infer_state.py:1712/1717`），而 `modeling.py`
  的两个调用点只判 `kvc.n_pages > budget`，把 None 直接送进要求四个张量的 pybind11 绑定 →
  `TypeError: scatter_pages(): incompatible function arguments`。触发条件是
  **prompt ≤ budget×page_size = 16×16 = 256**：`prefill_evict_extra_pages` 走
  `else: self.use_dci = False`（`:1960`，「无事可卸载」），随后 decode 越过 256 就崩。
  确定性，不是竞态——它杀掉了 llama-3.1 的 `multi_news` 第 96 行（日志 `Context length: 222`）。
  **这两处都是上游代码**（`git blame` → `63db4c11`，Yuzhen Mao，2026-04-04），HEAD 本身在这些输入上也会崩。
  修法：`if eids is not None: … else: assert not state.use_dci`——保留旧的响度，不静默跳过。
  **代价（必须写进表注）**：这些行的**整个 decode 都在 `use_dci = False` 下**，
  于是不建 page_scan 结构、不召回、不 scatter，`decode_sdpa` 传 `page_valid_entries=None`，
  decode 退化为固定 `c2p` 集上的普通分页注意力。**这些行两个 arm 都没算过**，
  在任何一个差异都藏在 `use_dci` 后面的 arm 下结果完全相同——是空测量，不是结果。
  判据是精确的：`token_length <= 256` 且 `token_length + generated_tokens > 256`。
  注意 `token_length` 逐元素等于日志里的 `Context length:`（95/95 行实测一致）。

### 9. page_scan 尾巴的 stash 复用 + H2D 直推 — `d86be89`（合并 `67428de`，报告 `17_`）

**TTFT −200…−390 ms（中心 ≈ −300），40 行 × 4 次启动 = 160 条记录逐字段相同（0 处不同）。**

改动的不是算法而是**谁在付释放成本**：每个 build 层的 K/V 原本 `k.clone()/v.clone()`，
16k prompt 下是 68 个张量 / 2.2 GB；分配藏在 worker 线程上，**释放没有**——
最后一个引用死在 `_page_scan_flush` 返回时，也就是主线程、TTFT 尾巴里，
glibc 给每个 32 MB 块 mmap，那次释放是 **68 次 munmap，实测占 1591 ms 尾巴里的 332 ms**。
改成**跨 prompt 复用的 pageable host 缓冲**；flush 也从 `torch.cat(...).to(device)`
改成每个 builder 一次 `copy_(non_blocking=True)` 直推进复用设备缓冲。

**代价必须声明：常驻内存 floor `VmRSS` +4.15 GiB**（峰值 `VmHWM` 反而低 500 MB）——
它把「每问一份工作集」变成「永久一份工作集」。在 156 GB 的机器上不阻塞，但不是免费。

**顺带纠正一个曾把这条线判死的前提：尾巴没有衰减，省的每一毫秒都是一毫秒 TTFT**（见第四部分）。

### 10. decode 查询路径：别名化 + 去 nonzero + query 常驻设备 — `6a229dc`（合并 `257e0d8`，报告 `18_`）

**TPOT −4.25 ms/token（88.910 → 84.659 ms，比值 0.9522，95% CI [−6.430, −2.072]），
9/9 配对全负，两臂范围不相交，每个配对都是 40/40 逐字段相同。**

四处改动：query 对 page_scan 留在设备上（不再 D2H 下去又 H2D 回来）；别名层的
`nr`/`rids` 不再 `clone()`；`_query_constants` 不再缓存 mask；`_scan_ops` 把会降级成
**三次 `torch.nonzero`**（每次都要 host 同步定输出大小）的布尔 scatter 换成「写进 `budget+1` 列再切片」。

**合并前由独立 agent 逐条反驳式验证**，最狠的一条是别名化——22 个别名层链式传递 `prev_nr`/`prev_rids`，
任何原地写都会沿链放大。结论：穷举静态追踪 + 运行时审计（336 张量快照 / 308 次别名 recall，**0 异常**），
`recall()` 在别名路径上根本不求值这两个参数，别名永远到不了 `_apply_selected_pages`，**那两个 `clone()` 是语义空操作**。
`_scan_ops` 与原序列在 **14/14** 用例上等价（含 all-reject、重复 id、`pos>budget`）。

**★ 对作者归因的更正**：收益的最大单项**不是** D2H 消除（0.710 ms/token，仅 17%），
而是**去 nonzero（1.31 ms/token）**；隔离探针合计只解释 ~60% 的 live 效应。

### 11. 上游竞态：prefill 的页表被 worker 线程截断（2026-09-26 发现，**未修，论文必须披露**）

`_page_scan_layout`（`infer_state.py:737-779`，截断在 `:758-759`）把 `kvc.c2p` 从 `[1,R]`
换成 `[1, budget] = [1,16]`（sink+window）。它跑在**卸载 worker 线程**上
（`modeling.py:145` 提交 `prefill_evict_extra_pages_wrapper` → `_page_scan_first_call` →
`_page_scan_layout`），而**主线程**在几条语句之后（`modeling.py:150`）的 `prefill_sdpa` 里
读同一个属性，把它交给 prefill kernel——但那个 kernel 的 plan 是按 **R 页**建的
（`infer_state.py:541` `n_kv_pages = ceil(q_len/page_size)`，`:547-549`
`kv_indptrs_tab = arange(0, bsz*R+1, R)`）。`batch_prefill.cu:79-115` 只查 dim/dtype，
**没有** `CHECK_EQ(paged_kv_indices.numel(), paged_kv_indptr[-1])`，就把裸指针交给 kernel（`:129`）。

worker 赢下竞态时，kernel 被告知「R 页」却拿到 16 元素的表，于是读
`paged_kv_indices[16 … R-1]` **越界**（最多 44 字节），每个垃圾 int32 又被当成
pool 页偏移解引用 → `CUDA error: an illegal memory access`。异步，所以在下一个阻塞调用处
才 surface（实测：下一行 prefill 的 `c2p` H2D，`kv_cache.py:230`）。

**可达性只需要 `R > budget`，即 `L > 256`**——本矩阵 3550 行里只有 2 行不满足，
所以几乎每一行都处在这个竞态下，只是主线程通常赢（`:140-142` 主线程只 join **上一层**的
worker 任务，本层的提交与读取之间没有同步）。`_page_scan_layout` 的 docstring
（`:784-793`）写着「`prefill_sdpa` 紧跟这次调用读 `kvc.c2p`」——作者知道顺序要紧，
但**没有任何东西强制它**。`_page_scan_defer_write` 默认关闭，与本竞态无关。

**这是上游的、与后端无关的**：DCI 路径在同一 worker 线程上有同样的截断（`:1246-1255`）。

**大多数赢是良性的**：被释放的块通常还留着旧 `c2p` 的尾部，越界读拿回的恰好是**正确**的页号；
只有当 worker 自己的 `PageScan` 分配复用了那个块时才致命。这与 ~3550 行里 1 次致命吻合。

**实测（2026-09-26，llama-3.1 `multi_news`）**：
- seed 117 → 第 119 行崩，两次，确定性；seed 118 / seed 119（进程里无带内行）→ 5 行全过。
- 同一序列加 `CUDA_LAUNCH_BLOCKING=1` **不崩** → **是竞态，不是确定性越界**。
- tokenizer 普查全部 16 个子任务 3550 行：带内行（`L∈[257,432]`，宽度会中途变化）只有 2 行，
  都在 multi_news（117 @ 314、199 @ 345）；已完成 1510 行的实测 `token_length` 与普查逐行吻合。
- 注意：**「带内行是必要条件」是概率陈述，不是确定性**。带内行改变的是时序，不是可达性。

**为什么本轮不改**：候选修法（把 join 加回 `prefill_sdpa` 之前，或把截断提前到 plan 建立之前）
都会动到 **prefill 的关键路径／TTFT**，而 TTFT 正是本文的结论轴；改了就得重测全部延迟数据。
本轮只采集准确率，所以**不动代码**，把这条作为已知的上游鲁棒性问题披露。
想确认它是否真的发生过（而不只是没崩），最便宜的探针是在 `prefill_sdpa` 调用点加
`assert kvc.c2p.shape[-1] == <plan 的页数>`——断言触发即证明竞态被赢下。**留待矩阵结束后的
独立进程里做**，且只能作为诊断，不能当成修法。

## 第二部分 · 失败的探索（**不要重试，除非有新证据**）

### 2.1 算法方向（结构性否决）

| # | 探索 | 判决 | 为什么 |
|---|---|---|---|
| 1 | **PAG 替换 DCI** | **否决** | 页尺度上：PAG 0.3161 ms/head vs 扫描 0.1544；build 10.4 s vs DCI 1.0 s；排序差 3–28%。**结构原因：build 是 O(N·max_search_k)，而 page formation 需要 `max_search_k ~ N` → O(N²)**，且不暴露聚类。一个 `O(log N)` 结构输给暴力扫描，是这个项目的复发性疾病。 |
| 2 | **batch-KNN dedup 重写** | **否决，而且是本项目最危险的一次** | 隔离测试里 **1.9x/2.6x 更快**，子操作表也确认了假设（`boolmask write` 确实是最贵的单 op，0.190 ms）——**然后 live 是 1.30x/1.34x 更慢**。诊断对，sign 错。 |
| 3 | **PAG-prefill k-means 打包** | 否决 | 严格 `pq` **−3.88 / −7.75pp**。 |
| 4 | **logsumexp / max / maxsm / seed 打分** | 否决 | 仪器和端到端**双负**。当时报的 +6.43pp 是**指标 bug**（见 3.6）。严格口径下，**page mean 打败所有 attention-mass 打分**。 |
| 5 | **fp16 贪心** | 否决 | 1.34x 快（不是 2x），但 PyTorch bmm 把**输出**舍入到 fp16，而行值 ~1e3，舍入 ~0.5 绝对值，**重排了 72% 的打包**（68% 的 token 换了页）。键本身是 fp16 精确可表示的，无用——问题在输出端。 |
| 6 | **分支 A：平衡递归分割（`lloyd:3`）** | 否决 | 离线仪器说**「准确率守住了」**（`pq` 0.5138 vs 贪心 0.5162，它自己标注为「a wash」，因为贪心自己的种子散布就跨 0.512–0.535）。**live n=200 是 −0.0158**（21 movers，16L/5W，p=0.027；两个 movers 是 1.0→0.0 的整体翻转）。这就是 `pq` 作为准确率代理失效的样子：−0.003 的 `pq` 变化 → −0.0158 准确率。 |
| 7 | **`lloyd:6`** | 否决 | n=200：−0.0122（16 movers，7W/9L，p=0.804）。注意它在离线反而是**更好**的划分（ceiling +1.6pp L2 / +1.0pp L20，且仍便宜 1.1x）——**ceiling 涨了，live 准确率还是掉了**。 |
| 8 | **分支 B：跨 head/层共享一个划分** | **用户先验否决** | 「一定会导致测试集准确率下降」。 |
| 9 | **分支 C：co-retrieval 感知划分** | 否决 | L2 +5pp 真实，**L20 上是 null**，且需要 `O(N²)` 逐头矩阵，与批量 `use_sim=False` flush 不兼容。 |
| 10 | **分支 C：逐头自适应 budget** | 否决 | 唯一能测出逐头真实需求的规则：**−0.276 / −0.402pp**。 |
| 11 | **分支 E：`page_size=8`（iso-token）** | 否决（null） | **离线每个仪器都赢**（严格 `pq` +7.29pp，`grp` +7.52pp，oracle ceiling +7.90pp），**live 准确率 −0.0063（等于没有），TTFT +1.035 s（200/200 更慢），TPOT +2.08 ms。** |

### 2.2 DCI 侧的具体改动（第 4 轮审计，全部有实测理由）

| 想法 | 判决 | 测量 |
|---|---|---|
| `calloc(max_leaves)` 补丁 | **不值得** | ctypes 直接量：1.273 µs × 32 head-tasks × 12 层 = **0.49 ms/token = TPOT 的 0.47%**。它守护的早停确实够不到（`prop_to_visit=1.0`），但它能省的钱就这么多。 |
| OpenMP 线程数调优 | **已是最优** | 1→64 扫：16.05 / 8.46 / 4.39 / 3.47 / 2.31 / 1.78 / **1.70 ms**。且 `output_mismatches []`——线程数可证明不改变选择。 |
| `num_to_visit` / `prop_to_visit` | **死参数** | 被 `dci_query` 里的 clamp 中和；死是安全状态。 |
| `num_neighbours` / `promotion_prob` | **活杆子但掉 F1** | 10.6x / 减半，docs 06/07 已测出代价。 |
| **DCI 查询整体** | **不可约** | perf 采样：`vecmul`（BLAS 距离）48.8% + 下降 28.9% = **78% 是下降本身和它算的距离**；E2 全排序 9.5%。没有一整块废代码。 |

### 2.3 page_scan 侧被否决的改动

| 想法 | 判决 | 测量 |
|---|---|---|
| **CUDA graph 捕获查询** | **被现有代码堵死** | 捕获失败：保序去重的布尔掩码写入降低成 `aten::nonzero`，`nonzero` 靠 D2H 确定输出尺寸，**捕获期间非法**。所以「让查询可 graph」=「重写去重」= 已被测出 live 慢 1.30–1.34x 的那个改动。**这两件事是一个决定，不是两个。** |
| 缓存 `c2p` 偏移 | **会引入 bug** | `c2p[0,0]` 在解码中会变，而整行不变式 `(c2p_a − c2p_b) == offset` **两种情况下都成立**，所以那个 assert 什么也证明不了。实测把 hotpotqa 第 1 行的 `Charles Laughton` 变成 `Charles Dickens`。 |
| 直接 pinned-fp32-CPU → fp16-CUDA 拷贝 | 无收益 | 164.7 vs 161.5 µs。 |
| 缓存 `out`/`first` 分配 | 收益低于噪声底 | `fill_`/`zero_` 重置是强制的（`scatter_reduce_("amin")` 是*归约进*缓冲区）。 |
| 折叠两个 `permute` / 切片 `c2p` | **对 TTFT 无效** | 值 ~534 ms，但改完之后 worker 已经**不在关键路径上**（DCI 2578 ms worker vs 3880 ms TTFT；page_scan 1793 vs 4743）。不是省不动，是省了也不动 TTFT。 |
| **CPU 页写 scatter 移植到 C++**（`scatter_pages_cpu`） | **不合并：live 是 null** | 代码正确、能走 `setup.py` 构建、24/24 行 prediction+score 逐字相同、11/11 对抗几何 0 差异、带内 verify 门也通过。**但 live A/B 里处理效应比它自己的空跑还小且变号**（A 块 −11.7 ms / B 块 +15.1 ms，同代码空跑 −18.9 / +7.9）。见下。 |

**★ 上一条的机制值得单独记：这个页写是 TLB 受限的，所以「索引更便宜」买不到东西。**
**〔2026-09-23 更正：「TLB 受限」已被直接证伪，见本节末尾的修正块。下面的推理保留原样，但不要再引用。〕**

隔离单调用确实快：numpy 284 ms → C `memcpy` 232 ms（**1.22x**）；对照能到 115 ms（2.47x，不可达）。
但**在真实并发下**（34 层做页写、8 线程、live 几何）numpy 455 vs C 441 = **1.03x**；
在现实的**连续**页范围上甚至是 **0.97x**（更慢）。
原因：THP 关闭时每个 512 B 存储落在不同 4K 页上，**两者都是 TLB 受限**，更便宜的索引迭代器省不出东西。
**〔更正：这个前提 2026-09-23 被证伪——给目的地 512 倍的 TLB 覆盖反而更慢，所以理由不成立。〕**
线程扫描 4/8/16/32 对两者都没帮助（numpy 364/297/308/321，C 311/291/309/320）——**8 线程本来就是对的**。
其它形状更差：目的序 gather 251 ms，整页顺序写 296 ms（**更慢**），NT stores 1597 ms（灾难）。

**这是 [[component-probes-nominate-live-ab-accepts]] 的第二次完整复现**（第一次是 dedup 重写）：
隔离基准把 op 的**排序**搞对了，把 live 的**量级**搞错了——1.22x 单调用 → 1.00x live。

**顺带修正 brief 里的两个数字**：`~296 ms` 是**第 7 行**的数；第 12 行是 ~300 ms 墙钟、
承载 **~2052 ms 聚合 CPU / 8 线程**。而且是 **34 层**在做页写，不是 12 层。
brief 还漏了两项：`f06_del` ~317 ms、H2D ~268 ms（greedy ~629 ms）。

**★ 2026-09-23 修正：上面「TLB 受限」的机制被直接证伪；中途一版「测不出效果」的结论本身是 NUMA 假象。**

把 pinned pool（`/dev/zero` shmem）用 `shmem_enabled=force` 强制成 2 MiB 大页，处理**确实生效**
（`pmd_lower_bound_frac_of_tensor` = 1.00，对照臂全为 0.0；`THPeligible`=1，`ShmemPmdMapped`=33,554,432 kB），然后测：

- **反面结论：给目的地 512 倍的 TLB 覆盖，页写反而慢 ~11%**（335.5–344.0 → 377.4–381.5 ms，中位数，两组不重叠）。
  所以这个页写**不是**目的地 TLB 受限的——上面那条理由作废。
- **一版「no detectable effect」的结论是 NUMA 假象，不是噪声。** 这台是双路 Xeon 5218，进程级 pinned 分配会随机落在
  本地/远端节点。直接证据：`contiguous_1t` 同代码跨进程在**不绑核**时散成 515–976 ms，
  `numactl --cpunodebind=N --membind=N` 之后复现到 <2%（node0 845.6–859.4，node1 843.4–857.4）。
  8 线程 scatter 本身的 node0/node1 差就有 **25%**（427–433 vs 340–343 ms）。
  **本节所有决定性数字都来自绑 node1 的那一遍**；生产的未绑进程看到的是更宽、不受控的分布。
- **源侧 THP 反而略快**（placebo 臂 `enabled=always`，stash 的 AnonHugePages 99.96%）：326.7/329.3 ms vs 335.5–344.0，
  即「目的地 4 KB + 源 2 MB」快 ~8–17 ms；而「目的地 2 MB + 源 4 KB」慢 ~35–45 ms。两端都是真处理，方向相反。
  **~10 ms 级别，低于噪声底，不值得收。**
- **单进程切换旋钮的死法值得记**：旋钮**生效**（`THPeligible`=1，可双向切换），但**大页不出现**——
  进程内已持有几十 GB 之后，新映射只拿到 0.07% / 29% 的巨大页，fresh 进程是 96–99%。

**同时作废的还有「~296 ms 不可压缩」这个印象。** 页写**不是带宽受限**：scatter 8t 只有 **13.2 GB/s**、
contiguous 8t **19.7 GB/s**，而本机 DRAM 约 250 GB/s（2×6-ch DDR4-2666）。所以 C 移植那个 null
也**不能**再用 TLB 解释（它的 live A/B 本身是 null，结论留着，解释换掉）。
局部性红利是 **~110 ms**（335.5 → 225.3），不是 ~300 ms；8 线程连续写的可达上界是 ~225 ms。

另：那台 bench 之前把 34 层写进**同一套 998 页**（真实布局是每层 `1032 + 1262*li` 起的独立块，各碰前 998 页），
工作集只有 1/34，也把旧测量**偏向 null**。

### 2.4 方向性否决（诚实记录，未启动）

**用 ANN 索引（HNSW/Vamana/FreshDiskANN）替换解码扫描、保留 DCI 的增量索引思想。**
原因：扫描在 P=8..64、B=3..32 上平在 **0.819–0.829 ms/(层, token)**，约占 106 ms TPOT 的 9.4%，
而 PAG 已经在那里输了。**杠杆在 build，不在 retrieval。**另外它要吊打的是一个 sublinear 结构
自己的遍历开销——这正是 PAG 输掉的地方。

## 第三部分 · 测量方法上的坑（第 II 类警示，同等重要）

这些**不是**失败的算法，是**会伪造出成功结果**的实验协议缺陷。本项目已栽过多次。

1. **组件探针提名，只有 live A/B 能采纳。** 三类案例：page_scan 的 CPU 写（反转的 gather+transpose 在隔离下
   3.4x **更慢**且写了不同的缓冲区）、fp16 贪心（合成计时说 1.34x，live 重排 72%）、dedup 重写（隔离快 1.9x，live 慢 1.34x）。
   **失败是不对称且危险的：隔离探针总能找到「看起来合理」的目标，所以它恰好在错的时候最有说服力。**
   案例 3 里 worker 在第一次 live 测量之前就已经把重写做完了。
   → **把每个组件拆分当成假设而不是结论；在写优化之前先跑能否决它的 A/B。**

2. **`--threads` 会限制 DCI 但不限制 numpy**，它凭空造出过一个假的 page_scan 加速。
   跨后端计时必须在生产线程数（64）。

3. **`--backends a b` 在同一个进程里跑两条臂**会污染计时（page_scan 因 DCI 臂常驻而慢约 1.5 s）。
   **每次调用只能一个后端。**

4. **只锁 GPU 不能隔离 TTFT 运行**：另一个进程的 CPU 工作会把 page_scan TTFT 抬高 0.6–2.2 s/行。
   任何作为**时间**上报的数字必须走 `quiet-run.sh`（双锁）。

5. **DCI 不可复现。** 同代码同 flag 的两次独立 n=200 运行，**18/200（9.0%）的行生成文本不同**（8 行分数不同）；
   **page_scan 是 0/200。**机制推测在 `dciknn` 的 OpenMP 并行树遍历的 tie-break。
   → **永远不要用 DCI 臂做正确性闸门**；任何涉及 DCI 的 A/B 必须带同代码空跑对照并报**不匹配率**。
   好消息：已发货的准确率余量（+0.021）约为 DCI 均值自身抖动（0.0011）的 20 倍，结论不因此推翻。
   **但它有一个必须记住的推论，报告 `16_` §3 把它量化了：同样这 40 行（第 0–39 行），DCI 的自身均值
   在历史上是 0.3864 → 0.4076 → 0.4208 → 0.4183 → 0.4226，跨度 0.0362，而 n=200 的全部优势只有 0.021。
   page_scan 在这 40 行上永远是 0.4042（逐位确定）。所以 9/21 那次 n=200 运行里这 40 行 page_scan 是赢的
   （+0.0178），今天同样这 40 行是输的 —— 符号翻转完全来自 DCI 在动，page_scan 一个字节没变。**
   → **任何低于 n≈200 的准确率 A/B 都是无信息的。不要做，也不要信。**

6. **page-recall 指标 bug（union-over-queries）** 曾把批评文档里每一个数字都抬高。
   **它会反转打分比较的 sign 却几乎不动打包比较**，所以无法从量级上发现——任何 recall 数字都要对照严格对照项。

7. **import 解析陷阱**：`icecache`/`icecache_cpp` 是指向主检出的可编辑安装，而 setuptools 把它的 finder
   追加在 `PathFinder` **之后**，所以**从工作树裸跑会静默执行主检出的代码，工作树的改动从不加载，且不报错**。
   修法：把两个未跟踪的 `.so` 软链进工作树 + 导出 `PYTHONPATH`。另有一个陈旧的 `site-packages/dciknn/`
   会退化成命名空间包（"unknown location"）。

8. **实验文档 03–10 描述的是一个已经不存在的代码修订版**——所有 `ICECACHE_*` 环境变量都已从 live 代码移除。
   它们的 DCI 侧否决**对今天的代码不具约束力**；读机制和测量，然后**回去检查它测的代码是否还在**。
   （同一文档列表里 page_scan 侧的否决是对当前代码做的，仍然有效。）

9. **`retrieval_stats.build_ms` 完全不含 `greedy_packed_pages`**，从它推断 TTFT 会低估 10 倍以上。

10. **`page_scan` 的 TTFT 有 CPU 争用混淆，而且 run-order 漂移是真实的、单侧的。**
    本轮 staging 的同代码空跑 29/11 **双方都出现**；prefill 的重复对照是 ±0.006 s。
    → 每个 A/B 都要空跑臂，并且**报分布形状不报均值**。

11. **★ 跨窗口散布可以大于任何窗内空跑——这是本项目第四个、也是第一个被「第二方复测」而不是被
    同窗对照抓到的一次。** staging 分支在自己的窗口里量到 **−22.3%** 原始 / **−17.7%** 净；
    13 条臂交错复测同一个改动得 **−13.3% ~ −14.9%**，差别不在合并、不在统计口径，而在
    **同一个二进制在两次测量里的绝对水平差 ~5.3 ms（~6%）**（opt 臂 82.1 ms vs 87.35 ms，同代码）。
    → **窗内空跑只能证明「这个窗口里 A 比 B 快」，不能证明「这个效应是这么大」。**
    三件事能防它：(a) **把被测对象单独作为一条臂放进同一个交错窗口**（而不是与别的改动合并后再测）；
    (b) **跑两个不同行的块**，看效应是否在块间稳定；(c) 报**跨窗口跨度**，不报单窗口的点估计。
    本次复测正是用 (a)+(b) 发现的——它的 `merged7 − stag1` 分解才是真正定位问题的那个测量。

12. **两份「独立复现」如果并发跑，就不是两个独立窗口。** 正面对决（报告 `16_`）里两个 agent
    各跑一份 4 臂实验，共用同一对锁，于是**各自的交错窗口里夹着对方的臂**。后果实测可见：
    复现 A 的 ps2 臂墙钟 7m13s 而 ps1 只有 3m38s，它的 `ps1−ps2` 空跑在 0–15 行漂了 −10.83 ms
    （比值 0.890），16–39 行只有 +0.55 ms（1.0065）——**漂移全在解码期争用，不是 warmup**
    （同时段 TTFT 没动）。**只跑 0–15 行的话，这个 19% 的效应会被报成 10%。**
    → **「独立复现」的价值在独立，不在复现数。** 要真独立就串行跑，或者至少把臂的**墙钟**
    和**分块空跑**都记下来；并发只买到 2 倍吞吐，买不到 2 份证据。

13. **子 agent 的 shell cwd 是主检出——相对路径会把改动写进错的那棵树。**
    后台 agent 的 Bash 从 `/home/yx/IceCache` 起，而且 harness 会在调用之间把它**重置回那里**
    （transcript 里就是那句 `Shell cwd was reset to /home/yx/IceCache`）。所以一个被要求
    「在 `.claude/worktrees/X` 里干活」的 agent，只要用**相对路径**编辑，就会写进共享的主检出，
    而它自己那棵 worktree（建对了、分支也对）**一个字节都没动**。
    实测：一个新 agent 的 `page_write.cu`/`page_write.h` 和它对 `infer_state.py`/`api.cu`
    的修改**只存在于主检出**里。后果是（a）worktree 的构建里根本没有这个改动，
    （b）任何以主检出为基准的测量都看到一个**半应用**的编辑。
    → **派活时必须给绝对路径，并明确禁止写 `/home/yx/IceCache/IceCache/...`。**

14. **★ 陈旧的 CMake glob 会静默产出一个不含你符号的 `.so`。**
    `icecache_cpp/CMakeLists.txt` 用 `file(GLOB CPP_SOURCES "src/*.cu")`，**没有
    `CONFIGURE_DEPENDS`**，文件列表在 **configure 时**就冻结了。在 configure 之后新增 `.cu`，
    构建会**成功**、import 会**成功**、新符号就是**不存在**——它读起来像「我的 kernel 慢」
    或「回退路径被触发了」，而不像构建错误。
    → **新增源文件后必须重跑 cmake。** 配套信号：`infer_state.py` 在
    `icecache_cpp` 缺少 `scatter_pages_cpu` 时会打印一行回退警告——**把它当作「我的构建是旧的」，
    不是「预期行为」。**

15. **worktree 里 `git status` 报 "expected submodule path ... not to be a symbolic link" 是良性的。**
    为了让 `3rdparty/{cutlass,pybind11,raft}` 可用而做的 symlink 会让 git 报这个错。
    它**只是外观问题**，不要为了「修好它」而退回到主检出里干活（这正是第 13 项那个 agent 掉进去的坑之一）。
    另注意：symlink `cutlass` **并不能**阻止 raft 的 `get_cutlass.cmake` 再 CPM 拉一份自己的
    到 `_deps/`——那笔 fetch 是省不掉的，网络是通的，等它跑完即可。

16. **★ 测量用的 `torch.cuda.synchronize()` 不是中性探针——它会改变被测的流水线。**
    在两个臂里加**逐位相同**的插桩，仅在贪心之后加一个 barrier，就把实测的 TTFT 差从 **~0 变成 −39/−91 ms**。
    barrier 强制一个平时被重叠的流水线串行化，于是贪心的节省被**当成端到端节省**暴露出来。
    → **插桩测量得到的差不是生产差值；报告时必须说明测的是哪一个。**
    这个形状现有代码早就知道：`SPEC_GREEDY_SYNC` 门控那个 sync，默认的计时区间
    `perf_counter()` 包着 `greedy_packed_pages(...)` **不带 sync**——所以那个数是主机**入队**时间，
    不是 GPU kernel 时间。**不标注就会被当成 GPU 开销读。**

17. **★ 本套 harness 能在 n=40 上凭空造出一个大赢。**
    有一次运行从一项**机制上最多只能产生 58.5 ms** 的改动里报出 **−245 ms** 的 TTFT 差——
    因为基准臂的 TTFT 水平是 **4053 ms**，而其他所有运行都在 3692–3850 ms。
    一个**4 倍不可能**的效应，纯来自运行级假象，而且很容易被当成 6% 的 TTFT 胜利报出去。
    同配置的两次复现**连符号都不一致**（−11.5 和 +26.6 ms）。
    → **诚实的估计量是「运行」而不是「行」**：三个不带插桩的生产路径配对给出
    −11.5 ± 12.7、+26.6 ± 22.4、−6.6 ± 9.8 → **运行级均值 +2.8 ms，运行间 sd 20.7，se 12.0，即 null**。
    行级合并固定效应（≈ −4.7 ± 7.3 ms）在运行间散布主导时**不成立**，引用它就是制造显著性。
    → **检查顺序：**（a）探针是否中性？（b）单位是运行还是行？（c）效应是否同时超过**同码 null**
    **和**运行间散布？**若实测效应大于机制上限，信机制，去找运行级假象**——
    但这是**判据不是先验**：不要因为效应大就否掉它（`tail-reaches-ttft-one-for-one` 里相反的结论
    是分别验证过的）。

21. **★ 分解里混用两套缩放律，会造出一个自洽但错误的预算。**

    所以把两者相加是**重复计数**。

### 准确率轴为什么关了

两条互补的证据，方向相反但结论相同：

- 贪心划分**打败** DCI 的 B+ 叶子 **+49%/+68%**（严格 `pq`），准确率只动了 **+0.021**。

最大的、经独立复算仍成立的 TTFT 动作**，但它**不是净胜**：把 217 ms 一次性搬进 decode。
**它的 TPOT 代价是常数、不是每 token 速率**（G=32 行实测 +0.228 s，而 40.6 ms/token 的
速率模型会预测 +1.258 s），所以 1.3803 那个 TPOT 比值里约 240 ms 是「除以 (G−1)」的
短答案归一化；按 token 加权的读数是 **1.1400**。

**⚠ 上面「下一步唯一清晰的杠杆」里那句「现在需要追回的只有 0.2723 s」用的是 `16_` 窗口的基线**
（该处已就地更正）。`19_` 窗口是 `total_s` 1.0540；本 A/B 的 OFF 臂 1.0540、ON 臂 1.0233。
**不要跨窗口引用这几个数。**
**并且：本 A/B 的 OFF 臂与 `19_` 的 page_scan 臂是同一条代码路径，两者差 61 ms（1.7%）——
这 61 ms 是 `21_` §6 里「ON 臂超过 DCI」那个 87 ms 边际的 70%。任何跨窗口的 DCI 比值
都需要在同一个窗口内补跑 DCI 臂，否则不要写。**

### 贪心线为什么关了（2026-09-23，两个 agent 反向作业后收口）

**不要把「批量无 mask 扫描」或它的任何变体重开。** 它看起来是显然的赢法
（贪心是 636 ms 的串行页步），但**是算术挡住的，不是噪声挡住的**，有两条互相独立的收口：

1. **候选比 [实测]。** 种子在范数序里每页前进约 **15.85 名**，几乎正好是 `page_size`。
   于是**可证明的鸽笼超集**需要 `|C| = σP + 1 ≈ 254` 行/页（σ=15.85，P=16）。
   为放 1 页算 254 行，把一趟约 0.5 FLOP/byte 的**内存受限**扫描变成约 120 FLOP/byte 的
   **计算受限** matmul，而 A100 fp32 的平衡点在 10 flop/byte 附近。**流量省的和 flop 涨的不往有利方向抵消。**
2. **逐位相同 [实测]。** `torch.bmm` 在 `[M,C,D]@[M,D,L]` 上只对 **C ≤ 16** 与逐行 `[M,1,D]` 形式逐位相同；
   C ≥ 20 时 cuBLAS 换 kernel，累加顺序变了。C=16 只给约 **1.01 页/次扫描**——等于串行、零收益，
   而且批量写输出比串行还大。**逐位相同的块大小和有用的块大小不相交。**

**那个把整条线框住的「带宽墙」是一个陈旧的 docstring 数字。**
`_greedy_packed_pages_live` **本来就已经 compaction 了**（`page_scan.py:355` 的
`live_k = k[head_col, live_idx]  # [M, L, D]`），bmm 的操作数是 `[M,L,D]`，不是 `[M,N,D]`。
真实的贪心构成（在 N=11770 上 profile，**引用时必须带 shape**）：

| 分量 | 代价 | 说明 |
|---|---|---|
| bmm | 156 ms / 约 375 ms 的贪心（**~42%**） | 223.9 GB，**1.434 TB/s = 峰值的 74%** |
| topk | 81.8 ms CUDA **+ 58.2 ms 自 CPU** | 精确性契约要求 |
| 记账 | ~110 ms | `scatter_` 2189 次、`copy_` 2265 次、`index_put_` 1472 次、`masked_fill(+_)` ~2200 次 |

**bmm 基本到底了**（峰值 74%、DRAM 受限、精确），现实余量（74%→90%）约是贪心的 **4%**。
把 profile 缩放到生产形状 N=16072（**统一按 `ΣL`，1.864**）：
bmm **291 ms（46%）**、topk **152 ms（24%）**、其余 **151 ms（24%）**，合计 595 ms 对 636 ms 的墙，
无逐项微调。独立锚点：`page_scan.py:300-303` 自己记的 N=16072 全宽 profile（793 GB、518 ms、1.53 TB/s），
shipped live 路径把流量砍到 ×0.522 → 414 GB → **271 ms = 43%**。**两条路给 43% 和 46%。**

**638 ms 里没有大的算法空间了。剩下的实现向杠杆只有一条：分支 `ceaf885`。**

> ⚠ **「再做一个紧凑化 topk」这个方向是错的，不要开**（2026-09-23 更正）。
> `ceaf885` 的 `_compact` **本身就是紧凑化 topk**——它的 `topk` 直接跑在 `[M, L]` 上、没有 `[M,N]` 回填。
> 所以 `page_scan.py:325-330` 那段「紧凑化 topk 不能保证 tie 一致、正是它逼出了 `[M,N]` scatter + mask + topk」
> 的断言**已经在 fp16 上被 17/17 的逐位相同测试证伪**（CUDA、生产形状 96×11770×128、span 1/3/默认、
> 五个强制 tie 形状、带一个会正确失败的负对照）；**fp32 上还没测，而 fp32 才是生产情形**
> （见下一条 dtype）。**并且「省下的量」是 `(1 − L/N) × topk ≈ 76 ms`，不是 152 ms，更不是 192 ms——
> 而这 76 ms 已经被 `ceaf885` 收走了**，把两者相加是重复计数。

**同一线上另外两条已实测的否决（都不要重试）：**
- **范数界 / Cauchy–Schwarz 剪枝剪掉 0%** —— 即使用**oracle** 界（真实的第 15 大分数），
  在 5888 个 head-page 上 keep-fraction 的均值 = 中位数 = **1.0000**。真实 key 范数近乎均匀
  （max/median 1.07–1.52），**没有范数结构可利用**。
- **2 级 topk** 快约 2.3x（0.112 → 0.022 ms），但 tie 跨组边界时无法证明语义相同。否决。

**分支 `ceaf885`（紧凑 live-set 贪心）尚未可合并** —— 三条理由都是**证据**问题，不是想法问题：
它的 tie 测试套件全是 fp32、span 边界回填在 `_self_test` 里从来没跑到
（`_greedy_packed_pages_self_check` 是**死代码**）、且它的 live A/B 跑在**落后 13 个 commit** 的树上。
预期天花板本来就小（约 50 ms / 3.7 s TTFT）：它只是把张量收窄，算子数和启动数不变，
而**它没碰的那趟扫描本来就已经 compaction 了**。已在 `89f3dca` 上 rebase 并补齐测试。

**★ dtype：fp32 是生产情形，理由是机制而不是观测（2026-09-23 定案）。**
这件事被三个 agent 反复争过，因为**两套证据都对、但说的是不同的张量**：

- `infer_state.py:152` **硬编码** `self.cpu_dtype = torch.float32`；`infer_state.py:1656` 也直说了
  *"`dst` is fp32 host (cpu_dtype) and `src` is the fp16 device pool"*。
- **device pool 是 fp16**（所以三个入口都硬编码 `torch_dtype=torch.float16`，device 路径上没有任何 cast）；
  **CPU offload pool 是 fp32**。
- 贪心拿到的 keys 来自 **CPU pool**（`tmp_cpu_kvc` → `offloaded_pages_cat[0]` → `_page_scan_first_call`），
  所以**贪心的输入是 fp32**。调用点探针打印的
  `keys.dtype=torch.float32 shape=(96, 11712, 128) use_sim=False` 就是它。
- 这也解释了另一个 agent 的「fp32→fp16→fp32 无损往返」（12,052,480 个值 0 变化）：
  那是 **fp16 的数值装在 fp32 容器里**，两个读数从来不冲突。

→ **推论：`ceaf885` 的 fp32 逐位相同性不是「潜在闸门」，它就是生产用例。**
fp16 上过 17/17 只证明了一个贪心见不到的 dtype。
（陈旧尺寸已在 `03bc9c4` 修好；那个 commit 是**纯 docstring**，
所以它**不可能**回答 dtype 问题——数值来自调用点探针，不是来自那个 commit。）

**★ 但生产情形既不是真 fp16 也不是真 fp32，这要单独写下来：**
`infer_state.py:1656` 那次拷贝是 **fp32 ← fp16 的加宽拷贝**（加宽是精确的），
所以冻结后的 keys 是 **「fp32 容器装着 fp16 精度的数值」**。
因此生产上的点积是 **fp32 累加、fp16 精度输入**——**精度严格落在真 fp16 与真 fp32 之间**，
它的 tie 密度**不能从任何一个端点推断**（实测 fp16 上 6–10% 的页在切点处 tie；纯 fp32 上 0/698）。
**这也是「fp32→fp16→fp32 无损往返」的原因：加宽拷贝精确，所以往返当然无损**——
机制**解释**了那个观测，而不是与它并存。
→ **引用 tie 密度 / 精度相关结论时，必须说明测的是哪一个 dtype，三者不能互推。**
