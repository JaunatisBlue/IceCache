# 双缓冲 + event 定序的尝试与中止（2026-09-12）

> 目标：做上一轮定的 ②（双缓冲 + event 定序）+ ③（同层内分块流水）。
> **结果：② 实现并跑通，TPOT −10.2%，但质量发生变化（F1 46.43 → 42.86）。按"不明白就
> 不发布"的纪律，已完整还原。下面记录全部证据与隔离矩阵，供下次快速接续。**
> 补丁留档：`apply_double_buffer_patch.py`（8 处改动，env 门控 `ICECACHE_DOUBLE_BUFFER`）。

---

## 1. 做了什么

把三块 transit buffer 从"单份共享"改成"2 槽 ping-pong"，并用 CUDA event 表达三个真实危害：

| event | 含义 | 记录位置 |
|---|---|---|
| `ev_read[p]` | 槽 p 的 **pinned 源**已可被 CPU 覆写 | c2g 上，H2D 之后 |
| `ev_cast[p]` | 槽 p 的 cast 已完成 | c2g 上，cast 之后 |
| `ev_used[p]` | 槽 p 的消费者（scatter）已读完 | default 流，scatter 之后 |

host 只在 `ev_read[p]`（**两层的槽**）上阻塞，于是第 L 层的 gather 与第 L−1 层的 DMA 交叠；
`scatter_pages` 改为 `current_stream().wait_event(ev_cast[p])`，用**流内顺序**替代 `c2g_stream.synchronize()`。

8 处改动：分配 2 槽（并处理 `cuda_cast_buffer is cuda_transit_buffer` 的**别名**）、`recall()` 绑槽 + 记录 event、`copy_to_buffer` 目标改为 `_ptb[b]`、H2D 前 `wait_event(ev_used)`、cast 后记录、调用点按开关跳过 sync、`scatter_pages` 按槽消费并记录 `ev_used`。

## 2. 效果：TPOT 确实降了

同一 2 样本、同配置：

| 配置 | TPOT | recall_wait | recall_gather | F1 |
|---|---:|---:|---:|---:|
| `DB=0`（原路径） | 137.83 | 48.50 | 9.68 | **46.43** |
| `DB=1` | **123.82** | **0.013** | 11.42 | **42.86** |

- **host 的 `recall_wait` 从 48.5 ms 掉到 0.013 ms** —— 同步点确实不再阻塞 host，机制成立。
- **TPOT −10.2%（−14 ms）** —— 与上一轮估的天花板（≈15 ms/token）吻合。
- **但 F1 从 46.43 变成 42.86。** 2 样本是确定性的（同配置重复跑都是 46.43），所以这是真差异。

---

## 3. 隔离矩阵：排除了三个候选原因

| 配置 | F1 | 结论 |
|---|---:|---|
| `DB=0` | 46.43 | 参照 |
| `DB=1` | 42.86 | 有差异 |
| `DB=1` + **强制恢复 host sync** | 42.86 | ❌ **不是 event 定序的问题** |
| `DB=1` + 强制 sync + **槽位固定为 0** | 42.86 | ❌ **不是槽位轮转的问题** |

**三个不同时序/不同槽位策略，都精确给出 42.86** —— 这排除了竞态（竞态不会如此确定），
也排除了 event 定序与槽位逻辑。**是一个系统性差异，来源尚未定位。**

对照：`DB=0` 在该文件状态下可重复给出 46.43（多次）。

## 5. 下一步诊断（明确的清单）

1. **差分取证**：在 `recall()` 记录每次的 `n_transit_pages` 与 `sum(nr)`，在 `scatter_pages` 记录 `nr.sum()` 与 transit 缓冲的**校验和**；
   同一 2 样本跑 `DB=0` 与 `DB=1`，逐次比对。
   - 若 `nr` / 选页**不同** → 差异在**选择路径**（说明改动间接影响了 DCI 结果，很可能是 OpenMP 归约顺序 / tie-break 对时序敏感）。
   - 若 `nr` 相同但**校验和不同** → 差异在**搬运路径**。
2. 若落在选择路径上：固定 `OMP_NUM_THREADS` 并多次重复，先量化 DCI 结果对时序的敏感度——
   这会顺带回答一个更重要的问题：**当前 baseline 的 F1 是否本身就不稳定**（若如此，那 0.23 F1 的 σ 里有一部分是算法不确定性，不只是采样噪声）。
3. 只有第 1 步定位后才能谈是否可用。

## 6. ③（同层内分块流水）为什么没做

`DCI.copy_to_buffer` 的目标寻址参数是
`offset_t = n_transit_pages * page_size * head_dim`、`page_size = page_size * head_dim`、`update_num = page_size`，
即**目标侧的布局依赖本次调用的总页数**。在没搞清这个寻址语义之前就分块，会直接把数据写到错位置——
上次"删 sync"已经吃过一次数据损坏的亏，这次不做第二次冒险。

**先把 `copy_to_buffer` 的目标布局写成文档（或加断言验证），再做分块。**
