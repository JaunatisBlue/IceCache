## 1. 端到端为什么还是慢：结构变了

| 分量 | page_scan | DCI | 差 |
|---|---|---|---|
| TTFT（每问付一次） | 3.6138 s | 3.3062 s | **+0.3076 s** |
| decode / 其余（`total − ttft`） | 0.4575 s | 0.4927 s | **−0.0352 s** |
| 合计 | 4.0713 s | 3.7989 s | +0.2723 s |

**和 `16_` 相比，结构变了：TTFT 之后的那个分量，符号翻过来了。**
`16_`：+0.0099 s（page_scan 略慢）；现在：**−0.0352 s（page_scan 略快）**。
于是端到端的全部差距都来自 TTFT，而且**只有 TTFT**——`total_s` 差 +0.2723 s，
TTFT 差 +0.3076 s，decode 分量倒贴 0.0352 s。这和 TPOT 领先 22.28% 是自洽的。

> 注：`total − ttft` 是**近似**分量，它包含每问的固定开销（打分、分词等），
> 不等于 `TPOT × 生成 token 数`（后者会更大）。用它只看**符号和量级**，不要当精确分解。

**盈亏平衡点：每问约 12.6 个生成 token。**
`(TTFT_ps − TTFT_dci) / (TPOT_dci − TPOT_ps) = 0.3076 / 0.0244 = 12.6`。
`16_` 的同一算式给出约 26–30（按其数字 0.5337/0.0203 ≈ 26.3）。**平衡点砍掉了一半以上。**
hotpotqa 实测生成 **5.82** token/问（page_scan 臂 6.350，DCI 臂 5.300–5.650）——
**还差约 2.2 倍，仍不达标**，但已经从「怎么都追不上」变成「再多生成一倍就翻盘」。

**生成 token 数是本轮唯一一个对 page_scan 不利的、且不受它支配的量：**
page_scan 四个臂全是 **6.350**（完全确定），DCI 四个臂是 5.300/5.475/5.625/5.650（**自己就不确定**）。
所以「每问慢 7.17%」里有相当一部分是它多说的那 0.84 个 token 换来的。

## 3. 噪声地板与稳健性

**同码 null（后端内部任意两臂，12 对 × 两序 = 24 个数）：**

| | `16_` | 本报告 |
|---|---|---|
| TPOT 最差 null | 6.7% | **4.68%**（ps3/ps1） |
| TPOT null 中位数 | — | **约 2.1%** |
| DCI 最差 null | 6.7% | **2.68%**（dci1/dci3） |

**效应是最大 null 的 4.8 倍、中位 null 的约 10.7 倍**（`16_` 是 2.8 倍）。

**槽位漂移没有出现。** 斜率和相关系数见 §0；作为对照，`16_` 的窗口里 DCI 在 A 段是 0.7%、
B 段是 6.7% —— 那才是需要保守修正的信号。这次两段的同码 null 落在同一分布里。

**诚实记录：少数同码 null 达到了名义显著。** ps2/ps3 的 TTFT（p=0.038）、
dci2/dci3 的 TTFT 与 `total_s`（p=0.0064）、dci3/dci4 的 `total_s`（p=0.017）。
36 个 null 比较里出现几个属预期。**值得注意的方向是：达到显著的都是槽位相邻（gap=1）的配对，
而不是跨窗口端点的配对**——如果存在单调漂移，应该反过来。所以这不构成趋势证据，
但它说明**单个配对的真实噪声地板约 2%**，这也是本报告坚持引用「16/16 全同向」而不引用任何单个配对的原因。

**效应相对地板：最小效应 19.43%，是最大同码 null 4.68% 的 4.1 倍。** 即使取最不利配对，判决不变。

## 4. 一次已披露的窗口重叠（诚实记录，判定：不影响结论）

贪心方向的第二个 agent 在我校正窗口安排之前，已经按早先的「你先用」指令取了 GPU，
在 **约 04:35–04:40** 跑了两条正确性检查（`dtype_probe.py`、`gpu_identity.py`）。
我的 `ps4` 臂是 **04:36:06–04:39:38**，**重叠了**。

**判定：不需要重测。四条独立证据：**

1. **文件系统证据把它的运行窗口卡在 04:35–04:40**：`greedy-2nd` 工作区里最后一个新文件是
   `gpu_identity.py`，时间戳 **04:35:07**，之后到 04:50 没有任何新文件落盘。
2. **偏差方向对我方不利。** 并发的 CPU/GPU 负载只会让 `ps4` 的计时**变差**，
   而 `ps4` 恰好是 **page_scan 臂**——任何污染都在**压低** page_scan 的成绩。
3. **`ps4` 没有任何异常名次。** TTFT 3.6321 在 {3.6153, 3.5679, **3.6398**} 里排第三（最差的是 ps3），
   TPOT 84.367 在 {83.278, 85.997, **87.179**} 里排第二（最差的是 ps3）。
   而且 **ps4 对 ps1（槽位跨度 7，最大）的 TTFT null 只有 −0.46%**，是所有 page_scan null 里最小的之一——
   污染会把这条推成大的正值，实测是反的。
4. **删掉 ps4 结论不变**：剩下 3×4 = 12 个配对依旧全部同向。

**教训（并入台账）：** `flock` 只做串行化、不做互斥声明。给另一个 agent 的窗口安排
必须**先发**、且校正要**立刻**发；一个「你先用」的旧指令会在几小时后仍然生效。
