# 合并后的正面对决 — `page_scan` vs `DCI`（同一交错窗口内直接测）

这是 §12.2 的**第一次直接测量**。此前所有「page_scan 比 DCI 快 1.13x → 1.29x」的说法，
都是**跨运行拼接**出来的：page_scan 的增量在一个窗口里量，DCI 的增量在另一个窗口里量，
再相除。这正是台账第三部分第 11 项警告的做法——本轮 staging 就是被它坑掉的（−22.3% 实测 → −14%）。

## 0. 结论

**是的，在合并后的代码上、在同一个交错窗口里，`page_scan` 在 decode 速度上明确赢 DCI。**
TPOT 比值 **0.785–0.857，中心 0.813**，即 DCI/page_scan ≈ **1.17x–1.27x，中心 1.23x**。
40/40 行全部同向。同代码空跑是它的 13%–20%。

**但是有一个和这个胜利同等重要的坏消息：**

| 轴 | page_scan | DCI | 比值 ps/dci | 判决 |
|---|---|---|---|---|
| **TPOT** | **88.19 ms** | 108.49 ms | **0.813** | **page_scan 快 18.7%**，40/40 行 |
| TTFT | 3.782 s | 3.248 s | **1.164** | page_scan 慢，36/40 行 |
| **`total_s`（端到端每问）** | **4.254 s** | **3.711 s** | **1.147** | **page_scan 慢 14.7%**，36/40 行 |

**hotpotqa 平均只生成 5.82 个 token（中位数外的分布：2–32）。** TTFT 的劣势要按每个 query
付一次，TPOT 的优势要按每个 token 付一次，而这个数据集根本没生成几个 token。
**盈亏平衡点是每问约 29.6 个生成 token**，实测是 5.82——所以在这份 benchmark 上，
page_scan **端到端更慢**。

§12.2 说的是「准确率**或** decode 速度至少一方面超过」。**decode 速度这一方面确实赢，而且赢得多。**
但「page_scan 让系统更快」这句话在 hotpotqa 上**不成立**，必须说清楚。

## 1. 方法

**两份独立复现**（两个 agent 各跑一份，互不通信），每份 4 条臂、臂交错、一个进程一条臂：

```
ps1 → dci1 → ps2 → dci2
```

`ps1/ps2` 与 `dci1/dci2` 是**逐字节重复**，也就是**同代码空跑**——这是本项目的标准配置。
`--threads 64`，`--page-size 16 --page-budget 16 --page-topk 0 --inject-pages off`，
`--n-reuse-layers 3`，hotpotqa 第 0–39 行，**每次调用只跑一个后端**（`--backends a b` 是已实测的混淆）。

**所有计时都来自 `quiet-run.sh`（双锁）**，没有例外。

### 代码版本

两个 agent 都跑在主检出 `/home/yx/IceCache`（`algorithm`）。
第一份的起止 HEAD 是 `6c290b1` → `917790a`，第二份起始 `917790a`。
期间我落了 4 个 commit（`2237181` `491a806` `ccdd712` `917790a`），**全部是文档移动/改字**——
`git diff --stat 6c290b1 917790a -- IceCache/` **为空**。所以 8 条臂跑的是同一份二进制。

### import 隔离（已验证）

```
icecache     -> /home/yx/IceCache/IceCache/source/icecache/__init__.py
icecache_cpp -> /home/yx/IceCache/IceCache/source/icecache_cpp.cpython-310-x86_64-linux-gnu.so
```

### 不是空转（已验证）

8 条臂每条都是 **72 次真实检索查询，`fallback_queries=0`**，且 `backend` 字段与臂相符
（ps 臂 `page_scan: 72`，dci 臂 `dci: 72`）。比较不是真空的。

## 2. 结果

### 2.1 合并统计（8 条臂逐行取均值后配对，n=40 行）

| 轴 | ps − dci | 标准误 | 比值 ps/dci | ps 更优行数 |
|---|---|---|---|---|
| TPOT | **−20.30 ms** | 1.08 ms | **0.8129** | **40/40** |
| TTFT | +0.534 s | 0.048 s | 1.164 | 4/40 |
| `total_s` | +0.544 s | 0.079 s | 1.147 | 4/40 |

### 2.2 逐对（每种臂序都算，防止某个顺序在系统性地贡献效应）

| 配对 | 复现 A 比值 | 复现 B 比值 |
|---|---|---|
| ps1 − dci1 | 0.790 | 0.843 |
| ps1 − dci2 | 0.785 | 0.787 |
| ps2 − dci1 | 0.826 | 0.857 |
| ps2 − dci2 | 0.821 | 0.799 |

**8 个配对无一例外，全部 < 1。** 范围 0.785–0.857 本身就是诚实的不确定度，
不要报点估计。

### 2.3 同代码空跑（这是判据）

| 空跑 | 均值 | 中位数 | sd | 0–15 行 | 16–39 行 |
|---|---|---|---|---|---|
| ps1 − ps2 | −2.70 ms | −1.33 | 7.57 | −4.08 | −1.79 |
| dci1 − dci2 | −4.09 ms | −4.06 | 6.45 | −2.95 | −4.85 |

空跑量级是效应（−20.3 ms）的 **13%–20%**。逐行配对 sd 是 ~6–8 ms，所以
**只有配对 + n=40 才让均值变得精确**（效应标准误 1.08 ms）。

### 2.4 跨窗口散布（第 11 项要求的报告项）

| 臂 | 复现 A 绝对 TPOT | 复现 B 绝对 TPOT | 相差 |
|---|---|---|---|
| page_scan | 88.436 ms | 87.953 ms | **0.55%** |
| DCI | 109.802 ms | 107.176 ms | **2.39%** |

**这一轮的跨窗口散布很小（0.55% / 2.39%）**，远好于 staging 那次的 6%。
这不代表第 11 项的教训过期了——代表这次运气好。两次复现都保留了自己的空跑，
所以即使运气不好也能看出来。

### 2.5 一个必须承认的污染

两份复现是**并发**的，都抢同一对锁。所以第一份的「交错窗口」里夹着第二份的臂，
反之亦然——**它们不是两个彼此独立的窗口**，是两个互相穿插的窗口。

实测的后果看得见：**复现 A 的 ps2 臂墙钟 7m13s，而 ps1 是 3m38s**，
而 A 的 ps1−ps2 空跑在 0–15 行漂了 −10.83 ms（比值 0.890），16–39 行只有 +0.55 ms（1.0065）。
也就是说 A 的空跑均值基本全来自那一段解码期的争用，**不是系统性的 warmup**（同时段 TTFT 没动：
ps2 前 16 行 3.866 s vs ps1 3.874 s）。

诚实地说：**如果只跑 0–15 行，或跨窗口拼接，这个效应可以被报成 10% 而不是 19%。**
这正是本次要检验的失败模式，而它确实出现在了数据里。效应在每个切法下都活着，空跑都没有。

## 3. 准确率：n=40 完全无法分辨，而且原因很具体

| 臂 | 第 0–39 行平均分 |
|---|---|
| ps1 / ps2（**5 次观测**） | **0.4042 / 0.4042** — 每次都一模一样 |
| dci1 | 0.4129（A 0.4076，B 0.4183） |
| dci2 | 0.4217（A 0.4208，B 0.4226） |

**page_scan 是逐位确定的：4 条 ps 臂 + 9 月 21 日那次 n=200 运行里的 ps 行块，
都给出同一个 0.4042。** DCI 同样这 40 行的历史值是：

```
0.3864   (9/21 n=200 运行)  →  0.4076  0.4208  (复现 A)  →  0.4183  0.4226  (复现 B)
```

**跨度 0.0362，而整个 n=200 的准确率优势只有 0.021。**

而且注意方向：在 9/21 那次 n=200 运行里，**这 40 行上 page_scan 是赢的（0.4042 vs 0.3864，+0.0178）**；
今天同样这 40 行，**page_scan 是输的**（0.4042 vs 0.41–0.42）。page_scan 的分数一个字节都没动——
**整个符号翻转都是 DCI 在动。**

结论与台账第三部分第 5 项一致，并且现在有了量化：
**任何低于 n≈200 的准确率 A/B 都是无信息的，不要做，也不要信。**
n=200 的 +0.021 仍然是站得住的（DCI 在 200 行上的自身抖动约 0.0011），
但它的**余量比 DCI 在 40 行子集上的自身漂移还小**——所以它脆弱，只在大样本上成立。

## 4. 这次测量改变了台账里的什么

| 台账原值 | 现在应改成 | 依据 |
|---|---|---|
| TPOT 优势「1.13x → ~1.18–1.29x」（跨运行拼接） | **1.23x（范围 1.17–1.27x）**，同窗口直接测 | 本文 2.1 / 2.2 |
| TTFT「落后 1.247x」 | **落后 1.164x**（合并树上直接测） | 本文 2.1 |
| （无此项） | **端到端 `total_s` 落后 1.147x** | 本文 0 / 2.1 |
| 准确率 +0.021 | 不变（n=200），但**必须注明 40 行子集上符号会翻** | 本文 3 |

**TTFT 1.247x → 1.164x 是变好了**，与台账「prefill 修复是共用的、会暴露 page_scan 的尾巴」
的预测方向相反。原因不明——这是一次直接测量，而 1.247x 是从两次 9 行的 A/B 相除来的。
按第 11 项，**以本文的直接测量为准**。
